## Incidents et vérifications notables

### Story 1.1

1. **Région du projet Supabase.** L'architecture prévoyait Paris (`eu-west-3`) ; le projet a été créé en Irlande (`eu-west-1`). L'écart a été repéré en vérifiant les réglages. Décision d'Abraham : garder l'Irlande (Union européenne, RGPD identique) ; l'architecture a été mise à jour.
2. **Recherche de secrets en échec au premier envoi.** L'action GitHub officielle de gitleaks a planté sur le tout premier envoi du dépôt (elle cherche le parent du premier commit, qui n'existe pas). Le journal indiquait pourtant « no leaks found ». Correction : lancer directement le programme gitleaks sur tout l'historique.
3. **Faux positif de la recherche de secrets.** gitleaks a signalé une « clé » dans `_bmad/_config/files-manifest.csv`. Vérification de la ligne : c'était l'empreinte SHA-256 du fichier BMAD `key-screens.md` (le mot « key » a trompé la règle). Exception limitée à ce seul fichier, documentée dans `.gitleaks.toml` ; toutes les autres règles restent actives.
4. **Relecture du code.** Un relecteur affirmait que l'outil `cn` venait d'un paquet npm inconnu. Vérification (`npm view cn`) : c'est le paquet officiel de shadcn ; remarque écartée. Un autre a trouvé que la commande d'envoi des migrations pouvait viser n'importe quelle base : garde-fou ajouté (refus hors développement).
5. **Erreur affichée dans le navigateur.** Un message « hydration » est apparu en mode développement. Les attributs en cause (`bis_skin_checked`, `bis_register`) sont ajoutés par une extension de sécurité du navigateur, pas par l'application ; aucune correction de code.

### Story 1.2

6. **Action bloquée par les permissions.** L'agent de construction a voulu envoyer la migration sur la base `nova-dev` ; le système de permissions de Claude Code l'a refusé. L'IA n'a pas contourné ce blocage : Abraham a relu le rôle de la migration (création seulement) puis l'a lancée lui-même.
7. **Relecture du code.** 18 remarques triées : 10 corrections (nom affiché lu dans la base, titre de la page, validation de la durée, test de l'état « Le serveur ne répond pas », vérification de la police et du survol…), 3 reports aux stories 1.3 et 5.3, le reste écarté après vérification (par exemple : les nouvelles tables étaient bien couvertes par le test de sécurité, qui parcourt toutes les tables).
8. **Serveur arrêté.** La page ne s'ouvrait plus : le serveur de développement avait été arrêté par l'application de bureau. Relancé ; aucun problème de code.

### Story 1.3

9. **Coupures de l'API.** L'agent de construction a été interrompu deux fois par une erreur 500 des serveurs d'Anthropic ; relancé à chaque fois là où il s'était arrêté, sans perte.
10. **Faux défaut d'accessibilité.** Le test « parcours au clavier » échouait : le premier Tab après l'envoi tombait sur le badge de développement de Next.js (`NEXTJS-PORTAL`), sans contour. Diagnostic par un test dédié ; le badge est désactivé (`devIndicators: false`), il n'existe pas en production.
11. **Relecture du code.** Un fichier de modifications vide a d'abord été envoyé aux relecteurs (erreur de commande) ; régénéré puis relu. 13 corrections, dont une faille de conception : la clé secrète du serveur pouvait écrire directement dans les tables et effacer l'historique. Migration 0004 : tout passe désormais par les fonctions contrôlées, prouvé par un test.
12. **Numéro de référence 0075.** La première demande manuelle a reçu `NOVA-2026-0075` : les 74 numéros précédents ont été pris par les tests automatiques sur la base de développement. Comportement voulu (un numéro n'est jamais réutilisé) ; la production partira de 0001.

### Story 1.4

13. **Migrations appliquées par l'agent.** Cette fois, le système de permissions a autorisé l'agent à appliquer les migrations 0005 et 0006 et à créer les comptes de test ; le compte administrateur d'Abraham, lui, a été créé par Abraham (mot de passe saisi par lui seul).

### Story 1.8

24. **Limite de connexions de la base gratuite.** Le premier test des 10 envois simultanés ouvrait 10 connexions directes ; avec les autres fichiers de test en parallèle, le pooler de Supabase (15 connexions au plus) a refusé des connexions et fait échouer des tests de la story 1.3. En local, `npm run test:e2e` réutilise un serveur déjà lancé : il faut l'arrêter avant, sinon tous les tests partagent la même IP et atteignent la limite.

### Story 1.9

26. **Limite d'appels de Supabase Auth.** Un premier test de l'action `connexion` faisait ~25 vraies connexions ; avec les autres tests, Auth a répondu « over_request_rate_limit » (429) et fait échouer des tests des stories 1.4 et 1.5. Ce test simule désormais Auth (la base reste réelle) ; les vraies connexions restent couvertes par `session.test.ts` et les tests du navigateur.
27. **Mot de passe court et API d'administration.** Le réglage « 8 caractères minimum » est actif (un membre qui choisit 7 caractères reçoit `weak_password`), mais l'API d'administration (`auth.admin.createUser`, clé secrète) ne l'applique pas : vérifié, un compte de 7 caractères y est accepté. Le test porte donc sur le choix du mot de passe par le membre ; les scripts et les futures invitations doivent vérifier la longueur eux-mêmes (`premier-admin.ts` le fait déjà).
